# PostgreSQL and private storage on your CachyOS server

Run these commands on **SERVER**, logged in as `ladmin`. Docker will run
PostgreSQL and SeaweedFS (private S3 storage). PM2 runs the Go API/worker and
Cloudflare Tunnel on the host; the frontend stays on Vercel.

## 1. Install Docker

Your login shell is Fish. Enter Bash for this setup:

```sh
bash
sudo pacman -Syu --needed docker docker-compose openssl nano
sudo systemctl enable --now docker
sudo usermod -aG docker ladmin
```

Log out and back in so group membership applies, enter `bash` again, then:

```sh
docker version
docker compose version
cd /home/ladmin/cogni-fresh
```

Docker group membership grants administrative control of the host; keep it to
trusted server users. See [Docker's Linux post-install instructions](https://docs.docker.com/engine/install/linux-postinstall/).
The [Docker](https://archlinux.org/packages/extra/x86_64/docker/) and
[Compose](https://archlinux.org/packages/extra/x86_64/docker-compose/) packages
are available in Arch's repositories.

## 2. Generate your environment and local certificates

On a **new installation**, replace the example below with your actual Vercel
frontend domain (the stable `your-project.vercel.app` domain also works):

```sh
bash scripts/server-infra.sh init https://learn.example.com
```

This creates a private `.env.production` with random database passwords, an S3
secret and `MFA_KEY`. It also creates `.local/server/tls` with a private local CA,
a localhost certificate and a trust bundle. It does not print the secrets.
The script refuses to overwrite either existing environment or certificates.

If you previously copied **only an unused template** into `.env.production`,
rename that template before initializing:

```sh
mv .env.production .env.production.before-infra
bash scripts/server-infra.sh init https://learn.example.com
```

Do not regenerate credentials for an installation that already has data. Keep
its environment and TLS files, and use `up` below. Existing external database or
storage installations can continue using their own credentials instead of this
local stack.

The initializer fills the connection settings for you:

| Variable | Generated value / purpose |
| --- | --- |
| `DATABASE_PASSWORD` | Random password for `workspace_owner`, used by the database container and migrations. |
| `APP_DATABASE_PASSWORD` | Separate random password for the restricted `workspace` application role. |
| `DATABASE_URL` | `postgres://workspace:GENERATED_PASSWORD@127.0.0.1:55432/workspace?sslmode=verify-full` |
| `MIGRATION_DATABASE_URL` | Same database using `workspace_owner` and its generated password. |
| `PGSSLROOTCERT` | Absolute path to `.local/server/tls/ca.crt`, used to verify PostgreSQL TLS. |
| `SSL_CERT_FILE` | Absolute path to `.local/server/tls/trust.pem`, containing public roots plus the local CA. |
| `SERVER_TLS_DIR` | Absolute path to the certificates mounted into the containers. |
| `OBJECT_ENDPOINT` | `https://127.0.0.1:59443` |
| `OBJECT_BUCKET` | `private-workspace`, created by SeaweedFS. |
| `OBJECT_USER` / `OBJECT_PASSWORD` | Local S3 access key and generated secret. |
| `MFA_KEY` | Generated once; retain it across deployments. |
| `PUBLIC_ORIGIN` | The frontend domain supplied to `init`. |

**No manual password copying is needed.** Both Compose and the backend read the
same `.env.production`. The database/storage use verified TLS; no application
security checks need to be disabled for localhost.

## 3. Fill in your SMTP and optional model settings

```sh
nano .env.production
```

Replace these entries with your mail provider's settings:

```sh
SMTP_ADDR=smtp.YOUR_PROVIDER.com:587
SMTP_FROM=security@YOUR_DOMAIN.com
SMTP_USERNAME='YOUR_SMTP_USERNAME'
SMTP_PASSWORD='YOUR_SMTP_PASSWORD'
```

The provider must support STARTTLS with a trusted certificate. These credentials
come from the provider; the project cannot generate working Internet mail
credentials. Mailpit is only a development inbox and is not part of this stack.
Invitations, verification and password recovery depend on working SMTP.

If using Gemini, set `GEMINI_API_KEY`; otherwise configure your selected provider
as described in [CORE-EDUCATION.md](CORE-EDUCATION.md). Keep the database, storage,
MFA and TLS settings generated by the initializer. Leave the three
`OMRCHECKER_*` path overrides empty. Use Bash quoting for secrets containing
special characters; keep `.env.production` private and out of Git.

## 4. Start the containers and apply migrations

```sh
bash scripts/server-infra.sh up
bash scripts/server-infra.sh status
bash scripts/server.sh build
bash scripts/server.sh migrate
```

`up` uses **compose.server.yaml**, not the development `compose.yaml`. PostgreSQL
starts with the `workspace` database and restricted runtime role. Migrations use
`workspace_owner`; default privileges let the runtime role read/write application
and River tables without becoming a superuser or schema owner.

If a container fails:

```sh
docker compose --env-file .env.production -f compose.server.yaml logs --tail 60 database objects
```

Keep these logs private. Do not print `docker compose config` or paste the full
environment into support messages; rendered configuration includes passwords.

## 5. Create your owner and start the backend

Follow **Build, migrate and create the owner** in
[SELF-HOSTING.md](SELF-HOSTING.md#3-build-migrate-and-create-the-owner) for the
one-time bootstrap command. Then:

```sh
uv sync --project omr --frozen
bash scripts/server.sh start
curl --retry 15 --retry-connrefused --retry-delay 2 --fail http://127.0.0.1:8080/health/ready
```

Finish the Cloudflare Tunnel and PM2 boot-persistence steps in the hosting guide.
Only the API goes into the tunnel. PostgreSQL listens on host loopback port
`55432`, and S3 on loopback port `59443`; do not add tunnel routes or router port
forwards for them. The API/worker use `127.0.0.1` because they run on the host.

## Persistence, restarts and existing credentials

Both containers use `restart: unless-stopped`; enabling Docker at boot restores
them after reboot. Their data lives in named Docker volumes, separate from the
development volumes. Application releases do not recreate data.

```sh
# Stop without deleting data:
bash scripts/server-infra.sh stop
# Start again:
bash scripts/server-infra.sh up
```

Never run `docker compose ... down -v` against data you need: `-v` deletes the
database and private files. Volumes are not backups. Back up PostgreSQL, S3 data,
`.env.production` and the TLS directory before upgrades; see
[OPERATIONS.md](OPERATIONS.md#backup-and-restore-qualification).

PostgreSQL's initialization scripts/password settings apply to an **empty data
volume only**. Editing `DATABASE_PASSWORD` or `APP_DATABASE_PASSWORD` later does
not change existing PostgreSQL roles. Rotate passwords in the database and
environment together; do not delete volumes to repair a password mismatch.
SeaweedFS also persists its credential state; retain the generated S3 keys.
See the [PostgreSQL image documentation](https://hub.docker.com/_/postgres) and
[SeaweedFS mini setup](https://github.com/seaweedfs/seaweedfs/wiki/Quick-Start-with-weed-mini).

The server certificate lasts 825 days; the local CA lasts 10 years. Check its
expiry with `openssl x509 -in .local/server/tls/server.crt -noout -enddate`.
Before expiry, renew using the existing CA/key/CSR and restart both containers:

```sh
openssl x509 -req -in .local/server/tls/server.csr \
  -CA .local/server/tls/ca.crt -CAkey .local/server/tls/ca.key -CAcreateserial \
  -days 825 -extfile .local/server/tls/extensions -out .local/server/tls/server.crt
docker compose --env-file .env.production -f compose.server.yaml restart database objects
```

Do not regenerate `MFA_KEY` or replace certificates/credentials by rerunning
initialization during routine deployments.
